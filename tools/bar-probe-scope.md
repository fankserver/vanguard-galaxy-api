# Independent-author bar probe

Prepare an isolated `Full` sandbox with `-BarProbe -BarAuthorABin <A Release directory> -BarAuthorBBin <B Release directory>`. Use committed, reviewed binaries from the exact `BuildRevision`. The standard launcher owns preservation, input hashing, process bounds and cleanup. The bar-only branch is selected from prepared provenance, not an arbitrary runner argument.

The vanilla fixture must load at a real station. After its initial native `CheckUpdatePatrons(false)`, controlled preparation calls the real `CheckUpdatePatrons(true)` at most eight times, one per frame, until at most three vanilla patrons remain. It never deletes patrons or fabricates seats. Failure to obtain capacity fails the run. The count of forced refreshes and retained vanilla patrons is recorded in `owned-bar-preparation.txt`. This setup is not a naturally sparse-station claim or a daily-time-transition test.

The phase checks two independent authors sharing a local ID, repeated native check-update calls, two actual station bar UI openings, native owned interaction dispatch and stale-contact refusal, finalized member order against actual native objects, exact vanilla JSON contents and metadata beneath owned presentation, exclusive denial/conflict, same-process save/reload without replacement placement calls, stale-session refusal and runtime provider removal/re-registration.

For a planned three-process sequence, add `-BarColdSequence` at preparation. After the producer launcher finalizes successfully, run the same sandbox with `-BarColdPhase absent`, then `-BarColdPhase consumer`. Both transitions require the preceding finalized success, preserve prior evidence, and claim a one-use phase marker. A failed phase cannot be retried. The save and API state remain in their original canonical directory.

The absence process deliberately leaves both author providers unacquired (their assemblies remain installed), verifies zero owned presentation, and saves over the same canonical slot. The absence save must change the native file hash and commit a new API snapshot at the same canonical path. The probe independently hashes the native file and reads the corresponding disk generation through the store's integrity decoder; it does not invoke owner capture or publication. The launcher rejects unchanged or mismatched generation receipts. The consumer verifies its restored path/hash and disk association against that finalized absence generation, then registers both definitions without calling Place and requires the saved owner identities and seeds to reappear. This qualifies registered-provider absence, not missing binaries.

It does **not** qualify Foundation/Anima/TTS composition, consumer-authored dialogue, natural daily refresh, missing author binaries, or linked story restoration. Those remain separate acceptance cases. A PASS requires the exact receipt plus the launcher's standard success and preservation checks.
