# Mission transitions — experimental 0.1.7

Opt in with `[Missions] Enabled = true` in `vgmodapi.cfg`, then query the `mission-transitions` capability and `ModApi.Missions`. This adapter binds only on the inspected game assembly and requires the lifecycle capability. Availability is not runtime qualification. Issue #11 remains incomplete: journal/provider adoption and further qualification are separate requirements.

`IMissionEvents` supplies immutable `MissionTransition` payloads with an observation sequence and `MissionSnapshot`. A snapshot separates the mission definition from the live instance, copies objective tags without collapsing them to one archetype, and records whether acceptance was actually observed. The producer owns no persistent history.

## Identity and restoration

The foundation's instance GUID is stable for an observed live occurrence within its session. Different objects sharing a story definition remain different instances; re-acceptance after an observed removal starts another occurrence even when an object is reused. Restored missions do not fabricate acceptance. Reset invalidates pending observations and identity mappings, so rollback/load never silently becomes a new acceptance. Optional cross-load correspondence requires `[Missions] IdentityContinuity = true` and coordinated persistence. The `mission-continuity` capability indicates its hooks/provider are available, not qualified. Identity records are captured around the actual `SaveGame.SaveCurrentState` factory and associated with its returned root object. Store must use that object with unchanged mission fingerprints; unknown/copied roots refuse identity capture rather than consulting later live state. Normal persistence commit/recovery gates still apply.

Only unique serialized mission fingerprints match a restored ID. Identical duplicates are deliberately omitted from persisted correspondence: they receive new session-local identities rather than an ordinal guess, without changing owner bytes merely because their runtime GUIDs changed. Snapshot hashes include the list/guild container and exact native JSON text; serialization differences conservatively lose a match. `IdentityEvidence` distinguishes `SessionOnly`, `SavedSnapshotMatch`, `MissingOrAmbiguous` and `Unavailable`. A match does not imply the journal has an acceptance record; `AcceptanceObserved` remains false for restoration. Corrupt/future/unreadable owner data is unavailable, not empty known history. Arbitrary foreign mutation of vanilla serialization remains outside the inspected contract. Weak identity keys do not retain every departed vanilla mission indefinitely.

Identity correspondence uses the reserved persistence owner `vgmodapi.mission-identities`, owner schema 1. Its bounded `VMI1` payload contains at most 4096 fingerprint/GUID records (8-byte header and 48 bytes per record); GUID bytes use .NET's `Guid.ToByteArray` layout. Inspection refuses any individual native mission JSON text larger than 4 Mi characters. No mission or history is truncated to fit. Missing owner data and indistinguishable records both report `MissingOrAmbiguous`: neither establishes correspondence. A refused identity capture prevents publication for **every coordinated owner**, including journal and stockpile, and pauses their mutations until coordinator recovery; an observer fault requires restart. The coordinated-persistence capability detail records the last identity refusal. Capability availability still describes installed functionality, not current mutation permission. A changed root, missing factory association, observer fault or protected owner state refuses capture through the existing coordinator, rather than committing guessed identity. Identical-byte and recovery limitations in the persistence contract still apply.

### Ordering relative to lifecycle subscribers

Restored transitions dispatch synchronously inside the API's PlayerReady callback, before later lifecycle subscribers receive PlayerReady. Reset consumer state on SessionStarting/invalidation, **not** on PlayerReady after restorations have arrived. Use the snapshot's SessionId and the already-updated CurrentSession to associate restorations. A consumer that initializes storage at PlayerReady must buffer these observations until its own initialization finishes. Subscribing later does not replay restorations.

## Proof and ordering

Internal observation scopes reserve logical order at entry, then accept verified state changes rather than successful method returns. An adapter must provide facts from actual membership, failure flags, archive count changes and reward-associated removal. Names, definition IDs and objective tags are copied at method entry (or at PlayerReady for restored membership). The native object available during dispatch can already reflect later nested mutations. Archive attribution requires a matching enclosing completed-removal scope; unrelated definition-only archive calls do not invent instance identity. A completion proof must come from a reward claim that actually removed the mission; direct removal with a completed flag is not by itself reward completion. Forced completion still requires that removal proof. No-op acceptance or ineligible reward claims emit nothing.

Each native operation requires its own scope; do not combine removal and reacceptance into one scope. The adapter must pair scopes with Harmony finalizers or try/finally, including exceptional exits. Closing an outer scope unwinds any unclosed inner scopes without throwing; entirely abandoned scopes require session reset or adapter recovery, not reliance on a skipped postfix. Nested scopes publish only after the outer operation settles, in reserved logical order. Thus an outer failure precedes its replacement's acceptance, and completion precedes nested archive notification. Repeated signals of the same kind for a live occurrence are deduplicated. `Removed` is a membership observation, distinct from a terminal outcome. The adapter must suppress misleading abandonment during a failure and witness transient insertion if a mission fails/removes itself during acceptance; final before/after membership alone can miss that insertion.

Sequence is monotonic across sessions for the producer's lifetime. Consumers must tolerate future unknown transition enum values. Membership includes the separate current bounty, patrol and industry slots, not only the missions list.

All access is main-thread-only. Subscribers must not mutate in-progress vanilla operations. Their exceptions are isolated. Session replacement during notification stops stale delivery; disposal drops queued observations. Snapshot objective tags are a copied set, not a reference to mutable vanilla lists. An optional `IVersionSensitiveMissionAccess` interface resolves only the exact snapshot currently being dispatched. The returned object is a version-sensitive vanilla mission, not a portable contract: inspect/copy it read-only during the callback, never mutate or retain it. Copies, old snapshots, reset sessions and access outside dispatch are refused. No mission construction API is provided.

## Inspected source constraints

On inspected game0.8.2.3, `AddMissionWithLog(Mission,bool)` may return without insertion for a duplicate story ID. `ClaimRewards(bool)` can reject eligibility, or remove after rewards when eligible/forced. Removal nests archive for story missions; failure sets its flag before notifications and may remove the old mission and force-add a replacement. There is no inspected per-live-instance GUID on the basic Mission object. The adapter samples these boundaries with guarded prefixes/finalizers, preserves vanilla exceptions, and never invokes eligibility checks itself. Membership scopes also observe the three vanilla guild board launch callbacks, Industry/Patrol reward overrides and tutorial bulk-clear. Changes discovered at scope exit follow nested verified completion/failure, and do not duplicate a witnessed removal. New slot membership can be witnessed before an inner failure/removal. Sweep snapshots are copied at discovery; removed entries retain entry-time snapshots. Arbitrary overrides bypassing these methods and direct mutations outside these scopes remain unobserved. Native qualification uses disposable generated missions and a temporary story factory, not a migrated third-party provider.
